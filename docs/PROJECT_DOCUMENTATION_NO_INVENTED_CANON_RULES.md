# Project Documentation Policy — No Invented Information

**Established from direct user instruction on November 9, 2026:** “make sure when you create documents you dont make up any information i havent approved”.

This policy controls future authoring and revisions for the Bear Cub Streamer / Acorn HoneyDweller project. It is a **documentation rule**, not a new fact about the fictional world.

## Rules for every future document

1. **Never invent unapproved story facts.** Do not add characters, names, ages, dates, family relationships, occupations, physical details, world laws, platforms, staff, viewers, interactions, dialogue, past incidents, numerical measurements, technology mechanisms, locations, events, outcomes or causes unless directly approved or explicitly supported by existing approved canon.
2. **User-approved fact vs inference:** Treat direct owner decisions and corrections as authoritative. If a connection follows from approved facts but was not directly selected, state **INFERENCE** and its basis, not “APPROVED.” If uncertain, label **UNKNOWN / UNAPPROVED**.
3. **Evidence required:** For substantive canon claims, link to an exact GitHub direct decision record or another existing primary user-approved source. Do not invent original quotations for earlier rounds. Original Q6–17 primary messages have not been fully recovered; do not upgrade working-bible summaries into verified direct quotations.
4. **Missing information stays missing.** Use explicit empty fields such as **UNKNOWN**, **NOT DECIDED**, or **PENDING OWNER APPROVAL**. Do not fill story holes for narrative smoothness or to make a finished document look polished.
5. **Even plausible proposals are not facts.** Do not introduce invented concrete examples, hypothetical events, fake transcripts, proposed new technology or new people in canon summaries. If the user **explicitly requests brainstorming, options, paper testing or hypothetical scenarios**, keep them in a separately marked draft, with every speculative element unmistakably **NOT CANON**, and seek approval before incorporation.
6. **Do not silently alter previously approved canon.** Latest direct owner correction takes precedence only on the specific thing corrected. Keep unaffected earlier choices. Flag genuine contradictions instead of choosing a fix.
7. **Differentiate official outside-world research from world canon.** Web sources about wildlife, controllers, platforms and law describe the real world; citing them does not establish a bear-world fact, species trait or legal requirement.
8. **Preserve the current phase.** Approval to write documents or continue a roadmap is NOT authorization to write enacted scenes, simulate gameplay, make source code, generate images or advance fictional time. The user must explicitly request any such output.
9. **Audit changed material.** Before completion, cross-check every added concrete claim, especially counts, ages, timeline position, relationship, and who knows secrets. Check links/files by fetching the saved GitHub content. State plainly what remains unverified; don't claim a full repo audit when only selected files were checked.
10. **Never describe a proposed document as approved canon just because it was saved.** Directly approved facts and assistant-written structure are different. A future world-bible v2 candidate is **working / awaiting owner review** until explicit signoff.

## Practical source classification

| Label | Meaning | Permitted in approved canon document? |
|---|---|---|
| **APPROVED (direct user)** | Explicit user selection, correction or unambiguous statement | Yes, with source |
| **SUPPORTED EARLIER CANON** | Grounded in another source identifiable by document and evidence grade | Yes **only with grade/uncertainty clearly preserved**; don't falsely certify direct approval |
| **INFERRED** | Logical implication, not explicitly selected | Separate, labeled; never claim user approved |
| **UNKNOWN / PENDING** | Not decided, incomplete or source missing | Yes, as empty/open placeholder |
| **PROPOSED / EXAMPLE / RESEARCH** | Assistant-created alternative, thought experiment or public external comparison | **No as fact**; separate and noncanonical only when specifically requested |

## Handling older speculative documents

Past R1–R5 working reports include sections explicitly labeled **PROPOSED**, **CONDITIONAL**, or **PAPER TEST**. These are **not user-approved historical facts**, regardless of descriptive detail. Future canon consolidation must use the **direct decision records**, not mine those example sections for new lore. If an older document is ambiguous, quarantine its unsourced claim and ask for owner approval before repeating it as canon. Keep old records for provenance with visible historical/noncanonical notices when relevant.

## Release gate for a new canon document

For every claim: **(a)** Is it direct-approved? If yes, cite it. **(b)** If a grounded inference, label it as inference. **(c)** Otherwise use UNKNOWN or omit. Before publishing, verify no new names, time stamps, episodes, behaviors or numbers slipped in. **Zero invented canon details** is the acceptance target.

**This rule is directly requested by the user and remains in effect throughout the project unless they explicitly change it.**
